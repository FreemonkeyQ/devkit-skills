# 架构

两个互斥模式，用参数选。**默认只读**；只有 `migrate` 的执行阶段才改代码，且需用户逐批确认。

## 适用 / 不适用

适用：模块边界不清；想加测试接缝；遗留代码要现代化；换 API / 改数据结构 / 大规模重命名。

不适用：需求没定 → `/dv-grill`；只想知道某段代码有没有 bug → `/dv-review`；只是写代码 → `/dv-build`。

## 模式

### `shape`（只读）

1. 读代码结构，列出模块与依赖方向（谁调谁，是否有环）。
2. 找**深模块机会**：接口窄、内部实现可替换、调用方不需要知道细节。反例是浅模块（一层转发的中间人）。
3. 找**接缝**：能在哪里测试而不启动整个系统。优先已有接缝，能少加一个就少加一个。
4. 提 2 个方案对比（`DESIGN-IT-TWICE`）：各自接口、代价、对现有调用的影响。
5. 落盘 ADR：背景 / 选项 / 选择 / 后果 / 回滚。
6. 交接：要定细节 → `/dv-grill`；直接开工 → `/dv-plan`。

### `migrate`（分批执行，需逐批确认）

1. 判断是否**宽重构**（一次机械改动波及全库）。不是宽重构就退回 `shape` 或 `/dv-plan`。
2. 三段式：
   - **expand**：新增形态，与旧形态并存，CI 保持绿
   - **migrate**：按爆炸半径分批（按包/目录），每批一个工单，批间 CI 保持绿
   - **contract**：确认无调用方后删除旧形态
3. 每批写清：批次号、范围、验证命令、回滚方式。
4. 落盘迁移计划，交接 `/dv-plan tickets`。
5. 执行阶段每个批次单独确认，不一次跑完。

## 硬约束

- `shape` 不改代码，`migrate` 只在执行阶段改，且逐批确认
- 方案必须给回滚路径
- 不为了「更优雅」引入未被需求要求的抽象

## 自检

- [ ] 依赖图里有没有环，结论明确
- [ ] 接缝数量：新增了几个，能否更少
- [ ] 两个方案都写了代价，不是只写优点
- [ ] migrate 的三段齐全，每批可独立回滚
- [ ] ADR 已落盘

## 反合理化

| 我本来想说 | 现实 |
|---|---|
| 「一次性重构完更快」 | 一次改全库，出问题时无法定位 |
| 「这个抽象以后肯定用得上」 | 臆测的通用性是负债 |
| 「先改结构，测试用现有的」 | 没有接缝就没法验证迁移是否等价 |
| 「批次切细一点就行」 | 细切但横切（按层）仍然落不了绿 |
