# 调研

不是搜索一次就回答。要求：**每个结论追到一手来源**，并落成一个可引用的文件。

## 适用 / 不适用

适用：需要多步取证；比较多个方案；核实版本/行为差异；存在多种解释的疑难问题。

不适用：一次文档查阅就能答 → 直接答；要找某段代码 → 直接搜；要定位 bug → `/dv-debug`。

## 流程

1. **写清问题**。一句话问题 + 判定标准（什么算答上了）。
2. **列来源层级**：一手（官方文档、源码、规范、API 定义）> 二手（博客、摘要）。优先一手。
3. **取证**。每条结论附来源链接或 `文件:行号`。找不到一手来源的，标为「未证实」。
4. **交叉验证**。关键结论至少两个独立来源，或直接读源码验证。
5. **落盘** `docs/research/<YYYY-MM-DD>-<slug>.md`：

```markdown
# <问题>
## 结论（先给答案）
## 证据
| 结论 | 来源 | 可信度 |
## 未证实 / 反例
## 对当前项目的影响
```

6. **交接**：要据此做决策 → `/dv-grill`；要动结构 → `/dv-arch`。

## 硬约束

- 不把二手摘要当一手证据
- 不确定就写「不确定」，不编
- 长任务可交后台子代理，但结论必须由主流程复核后落盘

## 自检

- [ ] 每个结论有来源
- [ ] 区分了一手/二手
- [ ] 有「未证实」一节（空的也要写「无」）
- [ ] 结论是答案，不是资料堆砌

## 反合理化

| 我本来想说 | 现实 |
|---|---|
| 「搜到的第一篇就这么说」 | 一篇博客不是证据 |
| 「版本号差不多，应该一样」 | 版本差异常是问题本身 |
| 「结论直接说，不用写文件」 | 不落盘，下次重查 |
