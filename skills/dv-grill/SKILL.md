# 拷问式需求对齐

不是需求评审会，也不是 brainstorming。它只做一件事：**把还没定的问题一轮轮问完，然后落盘。** 问完不落盘，等于没做。

## 适用 / 不适用

适用：
- 只有一个模糊想法，不知道要做什么
- 有方案但心里没底，想被人挑刺
- 要跟产品/同事对齐，需要一份可引用的决策记录

不适用：
- 需求已经明确、只想写代码 → `/dv-build`
- 只想查资料或比方案 → `/dv-research`
- 已经有 spec、只想拆工单 → `/dv-plan`

## 输入

一句话想法 / 现有 PRD / 半成品方案 / 一段对话。没有输入就先问「你想做什么」一句，不要追问第二个问题。

## 流程

1. **建设计树**。把要定的事按依赖关系排成树：根是目标，每层是它的前置决策。
2. **算 frontier**。frontier = 所有前置已定的问题。只问 frontier 上的。
3. **每轮提问**。每轮 **≤5 个**，每个必须：
   - 编号 + 标题 + 正文（可含选项）
   - 给**推荐答案**，措辞让「是」= 接受推荐
4. **等回答**。不替用户答，不并行推进。
5. **重算 frontier**。已回答的推出下一层。循环 2–5 直到 frontier 为空。
6. **落盘**（强制，不可跳过）：
   - 术语敲定 → 写 `CONTEXT.md`
   - 有取舍的决策 → 写 `docs/adr/NNN-<slug>.md`
   - 整体结论 → 写 `.devkit/specs/NNN-<slug>.md` 草稿，标 `状态: 草稿`
7. **交接**：`下一步固定是 /dv-plan`。

## 提问格式

```
❓ **Q1** - **<标题>**：<正文，可含选项 A/B/C>

➡️ 推荐：<答案 + 一句理由>

---
```

## 产物

| 文件 | 内容 |
|---|---|
| `CONTEXT.md` | 术语表：词 → 定义 → 反例 |
| `docs/adr/NNN-*.md` | 决策：背景 / 选项 / 选择 / 后果 |
| `.devkit/specs/NNN-*.md` | 草稿规格，`dv-plan` 接手定稿 |

## 停止条件 / 自检

- [ ] frontier 已空，没有「以后再说」的问题被静默略过
- [ ] 每个未定项要么定了，要么标为「阻塞」并写明缺什么
- [ ] 三个落盘动作至少做了规格草稿
- [ ] 术语若与现有 `CONTEXT.md` 冲突，已显式指出并让用户裁决
- [ ] 没写任何代码

## 反合理化

| 我本来想说 | 现实 |
|---|---|
| 「问题问完了，总结一下就好」 | 不落盘等于没做，下次还要重问 |
| 「这个细节先假设，回头再确认」 | 标成阻塞项，否则它会变成返工 |
| 「一次把 12 个问题都问了效率高」 | 超过 5 个，用户会跳着答，漏掉的更贵 |
| 「用户没回，我先按推荐的写进 spec」 | 推荐答案是提问的一部分，不是决策 |
