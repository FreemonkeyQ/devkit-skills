# 侦察与约定发现

目标是用最小代价回答：这个仓库已经有什么、按什么方式写、这次改动该复用谁。侦察不是审计，也不是生成百科。

## 三档侦察

| 档位 | 触发 | 读取范围 | 停止条件 |
|---|---|---|---|
| L0 小改 | 单文件、文案、配置、已定位的一行修复 | 最近 AGENTS/CLAUDE；目标文件；1 个同模块代表文件 | 能回答“改哪里、是否已有同类实现” |
| L1 标准 | 新接口、新表、新依赖、跨模块、行为变化 | L0 + manifest/lockfile + lint/test 入口 + 同模块 2 个代表文件 | 能写出复用台账并说明新增理由 |
| L2 全量 | 用户明确说“接入 / 摸清项目 / 项目画像” | L1 + 目录职责 + 开放式约定扫描 + 冲突核对 | 由 dv-context 执行；不在普通 build 中自动触发 |

全量扫描不能作为其他任务的副作用自动运行。L0/L1 是小步侦察，不是简化版全量审计。

## 搜索顺序

1. **符号与路由**：按函数/类/接口路径/路由名/表名/任务名搜索；先看定义，再看调用方。
2. **同层入口对照**：新增或修改入口时，至少看 2 个同层入口文件（例如两个路由模块、两个 service），确认同一关注点是否一致。
3. **同模块代表文件**：优先同目录、同层、同职责的 2 个文件；不要拿另一个模块的“最佳实践”套过来。
4. **依赖清单**：manifest、lockfile、已有 import；标准库或框架能做的，不新增包。
5. **历史证据**：`git log -S<symbol>` 看是否有人做过又删掉；不要复活已明确移除的设计。
6. **外部来源**：只有前五步都没有时才查官方文档；库的版本以 lockfile 为准，不按最新版写代码。

## 各语言先看什么

| 语言 | 入口 | 复用信号 | 风格信号 |
|---|---|---|---|
| Java/Kotlin | `pom.xml`/`build.gradle`、Spring 版本、`application.yml` | 现有 Service/DTO/Repository、公共 writer、ArchUnit 规则 | 构造器注入、记录类型、异常包装、事务注解 |
| Python | `pyproject.toml`、`uv.lock`/`poetry.lock`、`ruff`/`mypy` 配置 | 现有 utils、fixtures、异常策略、async 边界 | 模块级函数还是 service 类、类型标注、测试组织 |
| Go | `go.mod`、`.golangci.yml` | 现有 error wrap、interface 粒度、`internal/` 边界 | context 传递、包职责、表驱动测试 |
| JS/TS | 包管理器 + lockfile、`eslint`/`prettier`/`tsconfig` | 现有组件、状态方案、日期/HTTP 工具、设计令牌 | 命名导出、目录共置、错误边界 |
| C#/.NET | `.csproj`、`Directory.Build.props` | 现有分层、EF Core 配置、测试项目 | 依赖注入、异步后缀、可空性 |
| PHP | `composer.json`、Pint/PHPStan | 现有 Action/Service/DTO、查询层 | 严格类型、命名空间、测试风格 |
| Rust | `Cargo.toml`、`clippy` 配置 | 现有 trait/错误类型、`sqlx`/`diesel` 用法 | 所有权边界、错误传播、测试组织 |

工具名只是示例。先确认真实配置和版本，不假定已安装。

## 代表文件怎么选

- 选最近修改过、仍在维护的同类实现，不选废弃示例。
- 选完整包含“入口 → 业务 → 数据访问 → 测试”的一条链路，而不是单个工具函数。
- 记录路径即可，不复制大段代码进回答；写代码时按它的命名、分层和错误处理来。

## 约定判定

一条约定要同时满足：

- **一致性**：至少 3 处一致示例，且没有数量相当的对立写法。
- **是选择**：框架默认、生成器默认、formatter/linter 已强制的形式不算约定。
- **会影响下一次写法**：没有这条，下一个 agent 很可能写成另一种。

出现两种写法并存时：

- 不输出“本项目约定是 X”；按台账格式写“冲突：<文件A> 用 X，<文件B> 用 Y”，并给出各自数量和代表文件。
- 至少核对这些同一关注点：会话/依赖获取（注入 vs 直接创建）、错误处理（统一包装 vs 裸抛）、数据访问（ORM/Repository vs 原生 SQL）、认证/租户过滤（中间件 vs 每个查询手写）、日志/配置（统一封装 vs 直接调用）、测试（fixture/工厂 vs 手写数据）。
- 只有用户给出稳定的目录/场景边界时，才把两种写法分别记录为局部约定。
- 证据不足就跳过，不为了显得完整而编造规则。

## 停止条件

- 能回答复用台账四问，就停止侦察，开始写。
- L1 标准任务的侦察约 15–20 次工具调用；超过约 30 次先检查是否在做无关审计。
- 连续读 3 个文件仍找不到同类实现，记录“未找到”，不要无限扩大搜索。
- 小改超过约 10 次工具调用或明显超过任务复杂度，回到 L0，先完成最小改动。
