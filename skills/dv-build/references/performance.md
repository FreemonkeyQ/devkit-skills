# 性能与 SQL 门禁

只有改动触及下列任一情况才触发；不要求每个任务都做性能审计。

触发条件：SQL/表结构/迁移、循环内 I/O 或数据库访问、无界集合或全量拉取、缓存、并发/线程/协程、分页、热路径、大文件或流式处理。

## 代码层

- 循环内是否发起数据库/HTTP/文件调用；能否批量或一次查询。
- 是否拉取无界结果；列表接口是否分页；是否有最大页大小。
- 是否在 async/事件循环里做阻塞 I/O；是否在锁内做网络调用。
- 事务/锁范围是否过大；是否在事务内做远程调用或文件上传。
- 是否重复分配大对象、重复序列化、无界缓存；缓存是否有失效策略。
- 重试是否幂等；批量写入是否分批，避免长事务和大锁。

## SQL 层

- **N+1**：循环里单条查询、ORM 懒加载集合、逐条 `findById`。优先批量 `IN`、join、聚合计数或 eager loading。
- **sargability**：索引列上不要套函数/表达式/隐式类型转换；避免 `LIKE '%x%'` 和大范围 `OR` 导致全表扫描。
- **分页**：深 `OFFSET` 改 keyset/seek（`WHERE (created_at, id) < (?, ?)`）；列表必须有上限。
- **索引**：按真实 WHERE/ORDER BY/JOIN 设计复合索引，遵守最左前缀；外键列确认有索引；索引不是越多越好，评估写放大。
- **投影**：宽表避免 `SELECT *`；列表只取需要的列。
- **聚合/count**：大表 count 可能很贵；能用 `Slice`、缓存或近似值时不要每次精确 count。
- **批量写**：批量 insert/update，分批提交；避免逐条写入和超长事务。
- **连接池**：确认池大小与超时；不要在请求里创建连接。
- **验证**：新改或新加的重要查询跑 `EXPLAIN`/`EXPLAIN ANALYZE`，看 `Seq Scan`、实际行数、`Sort`、是否命中索引。

## 证据要求

- 有 `EXPLAIN`、慢查询日志、行数或基准数据就贴关键结果。
- 没有实测就写“未验证/未实测”，不要仅凭改法声称“性能提升”。
- 不能连目标数据库时，说明缺环境，并给出可复现的验证命令。
- 性能建议与正确性修复分开报告；不要为了性能改变业务语义而不说明。
