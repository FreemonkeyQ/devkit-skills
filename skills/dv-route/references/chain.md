# 链路交接与目标式委托

`next` 是候选图，不是执行状态机。推进下一步只能由用户确认或事先声明的终点触发，且不改变任何技能原有的授权边界。

## 三行交接

每个技能收尾固定输出三行，不写成长篇总结：

1. **已完成**：实际动作、产物与证据；未验证项直接标注。
2. **建议下一步**：从 `metadata.next` 选 1 个默认；必要时附 1 个备选并说明理由。没有候选时写“无默认下一步”。
3. **需你决定**：只列影响下一步的真实决定；没有就写“无”。

示例：

```text
已完成：新增导出接口并通过相关测试，退出码 0。
建议下一步：dv-review（默认，改动含未提交文件）；备选 dv-test（若要补集成用例）。
需你决定：无。
```

## 默认下一步

只有 `next` 里确实有候选时才推荐，按下面顺序选，不跨出候选图：

- 实现或修复完成：有可用测试入口先 `dv-test`，没有或风险低再 `dv-review`；准备收口用 `dv-done`。
- 测试发现实现缺陷：回 `dv-build`；需求或环境问题停下确认。
- 评审通过或只剩收尾：`dv-done`，不要直接建议 commit。
- `dv-done` 之后默认建议 `dv-commit`；只有用户明确要推送或终点含 push 时才建议 `dv-push`。
- 设计交付后：实现用 `dv-build`，真实 UI 变更验收用 `dv-browser`。
- 候选都不合适或目标变了：回到 `dv-route` 重新编排，不硬套 `next`。

## 逐步模式（默认）

1. 输出三行交接后停下，等待用户确认。
2. 用户说“继续”“下个”“好”“按这个来”即视为授权调用建议的下一步。直接进入该技能，只读必要的增量上下文，不重新做完整侦察。
3. 用户改选备选、换目标或叫停时以新指令为准，不改写已完成技能的结论。
4. 下一步不在 `next` 中但用户明确要求时可以调用，但要点明这是偏离候选图。

“继续”只授权当前建议的那一个技能，不顺延到后续技能或 Git 动作。

## 目标模式

触发语示例：“根据 dv Skill(s)/技能执行”“按 dv 链路走完”“一直做到 done”“一直做到 done push”“从 build 做到 push”。

开工时先给链路计划，不直接连续跑：

- 起点 → 终点，例如 `build → test → review → done → commit → push`
- 预计技能序列，标出可跳过项及理由
- 本次停车闸门
- 本次授权范围：允许写业务代码、测试、文档，或只到 done 等

用户确认计划后连续执行。每个技能仍输出三行交接，但常规步骤不再逐次等待；只有命中停车闸门才停。

未声明终点时默认到 `done`，并在计划中写明；需要 commit、push、部署必须由用户补充或在计划确认时明确加入。

## 终点解释

| 用户说法 | 终点 | 不包含 |
|---|---|---|
| 一直做到 done | 验证与汇报完成 | commit、push、部署 |
| 一直做到 done push / 做到 push | done 后提交相关改动并 push | force、merge、PR、部署、审批、重试 |
| 做到 commit | 本地提交完成 | push |
| 走完开发链路 | build → test/browser（按风险）→ review → done | commit、push |
| 修好并验证 | build → test → done | commit、push |

终点未写 Git 动作就不 commit/push；终点写了 push 才在 done 后提交并推送，同时仍遵守 push 技能的保护无关改动、非 fast-forward 检查等规则。其他终点按用户字面解释，计划阶段先确认是否包含 commit/push/部署。

## 停车闸门

命中任一条即停，报告已完成部分、缺口和可选下一步：

- **范围变化**：新增需求、改动文件明显超出计划、要动无关模块。
- **未定决策**：产品口径、技术选型、设计方向或验收标准无法从现有证据决定。
- **不可逆或共享副作用**：数据删除/迁移、生产写入、审批、发布、force push、merge、PR、安装全局依赖。
- **Git 动作超出终点**：终点未包含 commit/push 却需要提交。
- **失败或阻塞**：验证失败且超出授权修复范围、同一缺陷两轮未修复、环境或权限缺失。
- **用户叫停或改目标**。

普通测试失败但本次已有实施授权、且属于原计划范围时，按 `dv-test` 的修复回路处理，不算停车。

## 授权

- 逐步模式的确认只授权建议的那一个技能。
- 目标模式的计划确认只授权计划内技能，终点和闸门以计划文本为准。
- 任何模式都不把 `effects` 或 `next` 当成额外权限；提交、推送、部署仍按技能原有 `explicit-actions` 和用户意图。
