# 业务规则到用例

为重要规则保留R编号、来源版本、适用角色/状态、输入、观察结果与副作用。

## 方法
- 等价类和边界：最小/最大、空/缺失、非法值；先确认输入在哪一层可达。
- 决策表：权限×状态×选项，组合爆炸时选关键交互/成对组合，不声称穷尽。
- 状态机：合法/禁止跳转、重复执行、回退、重连与取消。
- 时序：超时后响应、并发写、重复消息、先失败后重试、部分成功。
- 文件/批处理：中断、坏格式、编码、磁盘满、事务/恢复边界。

## 用例表
| 规则 | 前置 | 输入/步骤 | 期望 | 必须/禁止副作用 | 现有入口 | 优先级 |
|---|---|---|---|---|---|---|

缺规则写待确认；缺框架写自动化缺口，不删规则以迎合已有测试。
测试必须能失败在真实错误行为上，而非只验证mock期待已设置。

## 完整例子：订单取消

已确认规则：R1 只能取消本租户订单，跨租户与不存在均返回 not-found；R2 paid→cancelled 并发出一次取消事件；R3 已取消重试成功，但不再次写入或发事件；R4 shipped 拒绝取消且无副作用。

| 规则 | 前置 | 输入/步骤 | 期望 | 必须/禁止副作用 | 验证边界 | 优先级 |
|---|---|---|---|---|---|---|
| R1 | t2 的 paid 订单 | t1 用户取消 | not-found | 不改状态、不发事件 | 服务授权边界，另验实际API身份映射 | 高 |
| R1 | 不存在的ID | 取消 | not-found | 不写入、不发事件 | 服务 | 高 |
| R2 | 本租户 paid | 取消一次 | cancelled | 持久状态改变，事件含正确ID/租户 | 服务＋隔离存储/事件捕获 | 高 |
| R3 | 本租户 cancelled | 再取消 | 成功且仍cancelled | 无新增事件、无再次写入 | 服务 | 高 |
| R4 | 本租户 shipped | 取消 | conflict | 状态不变、无事件 | 服务 | 高 |

边界取舍：多数规则用服务测试快速定位；隔离集成测试验证真实持久化/事务，少量API测试验证身份与错误码映射。不因为API层更高就把每个组合都推到E2E。若并发、事务与事件原子性尚无契约，记录待确认，不从当前实现臆造规则。

弱断言：仅检查 `cancel(...)` 返回 success，会放过“状态未保存”“错误租户被取消”“重复发事件”等缺陷。

更有意义的断言示意（接口名是假设，执行时沿用项目已有设施，不安装框架）：

```python
# repo为隔离存储，events为捕获实际发出事件的边界；不是预先塞入期待事件。
result = service.cancel(order_id="o1", tenant_id="t1")
assert result == "success"
assert repo.get("o1").status == "cancelled"
assert events.sent == [{"type": "cancelled", "order_id": "o1", "tenant_id": "t1"}]

service.cancel(order_id="o1", tenant_id="t1")
assert repo.get("o1").status == "cancelled"
assert len(events.sent) == 1  # R3规定重复取消不能重复发事件
```

关键调用次数断言可验证明确的幂等契约，但不应要求任意私有函数必须调用一次。跨租户场景还应断言错误返回、原状态及事件不变；仅测试mock已设定的返回值不够。测试替身证明服务逻辑，不能单独证明真实数据库事务和事件投递可靠性。

## 检查断言是否有效

问：“如果删除状态保存、删掉租户检查或让重试重复发事件，哪条断言会失败？”这是假设性检查，不等于已执行突变测试；运行突变需既有工具与隔离授权。找不到对应断言时补覆盖，不能以高覆盖率或mock调用成功宣称业务正确。
