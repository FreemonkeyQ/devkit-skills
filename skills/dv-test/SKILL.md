# 测试

两个模式互斥，选错会做无用功：

| 模式 | 做什么 | 不做什么 | edits-code |
|---|---|---|:--:|
| `design` | 从业务规则推用例、边界、断言 | 不写测试代码、不跑工具、不装依赖 | false |
| `run` | 写/跑测试、修偶发、出报告 | 不重新设计用例、不改业务代码 | true |

## 适用 / 不适用

适用：开发前定用例（`design`）；用例遗漏检查（`design`）；补写测试或修 flaky（`run`）。

不适用：要评估测试是否真能抓 bug → `/dv-audit`；要修 bug → `/dv-debug`；要设计方案 → `/dv-design`。

## 模式 `design`

1. **明确依据**：读已确认需求、接口契约、项目约定。每条规则编号（R1、R2…），记录来源。
2. **识别现有设施**：读测试目录、运行配置、少量代表性测试。确认实际框架、入口、fixture、mock 边界、断言风格。**不因装了某个依赖就宣称已有该能力。**
3. **从规则推用例**：正常路径 → 边界 → 缺失/非法输入 → 状态变化 → 权限 → 依赖失败 → 重复操作与时序。
4. **每条用例必须回答**：依据哪条规则 / 什么前置条件 / 什么输入 / 期望结果 / 哪些副作用必须或不得发生。
5. **对照已有测试**：标出已覆盖、覆盖不足、完全缺失。
6. **交付**：规则清单 + 用例表 + 覆盖映射 + 缺口 + 验证办法。
7. 交接：要落地 → `/dv-build`（含 TDD）或 `/dv-test run`。

## 模式 `run`

1. 读现有测试与 `commands.testUnit` / `testE2E`。
2. 写测试：一个行为一个测试，断言具体结果。只测外部行为，不测私有方法、不断言 mock 调用次数。
3. 运行，收集输出与失败分类：
   - 断言失败 → 修实现或修期望（先确认哪边错）
   - 环境/偶发 → 隔离顺序依赖、检查异步、固定时间与随机源
4. 不稳定的测试：quarantine 并修，不允许「重跑到绿」。
5. 出报告：范围 / 结果 / 失败归因 / 覆盖率缺口 / 建议。
6. 交接：要评审改动 → `/dv-review`；要验证测试有效性 → `/dv-audit`。

## 硬约束

- `design` 不产生测试代码，`run` 不重新设计用例
- 不从实现反推「正确行为」
- 缺测试不自动等于 bug
- 不装新框架来「补足」现有设施

## 自检

- [ ] 模式明确，没有两头都沾
- [ ] 每条用例都能追溯到一条规则
- [ ] `run` 报告含失败归因，不是只列数字
- [ ] 没有用 skip / 放宽断言掩盖失败

## 反合理化

| 我本来想说 | 现实 |
|---|---|
| 「边设计边写，效率高」 | 两个模式的产物不同，混做会漏掉边界推导 |
| 「覆盖率 80% 就够了」 | 覆盖的是代码行，不是业务规则 |
| 「这个测试老是挂，跳过了」 | 偶发是缺陷，不是噪音 |
| 「按现有实现写用例」 | 那只是把 bug 固化成预期 |
