# 用例设计与测试执行

## 适用 / 不适用
设计业务场景、补测试、执行与维护测试。实现缺陷在授权与范围内按build规则自动修复并复测；根因不明或需产品决策用debug；测试有效性审计用audit；真实UI验收用browser。

## 模式
- `design`：读取规则与现有设施，输出用例/覆盖缺口，不写测试代码或运行工具。
- `run`：写/跑测试与报告；可补必要场景和断言，不重新展开完整需求规划；发现实现缺陷时进入修复回路，环境或用例问题只报告。
- 无参数时从用户动词选择；歧义才问。

## 流程
1. 规则来源优先于实现；明确权限、状态、输入、期望结果及必须/禁止副作用。关键规则编号方便追溯。
2. 确认项目实际框架、运行入口、fixture、依赖边界与版本；无设施时给手工/替代验证，不凭依赖文件假定工具能运行。
3. 按适用性推正常、错误、边界、并发、重复、取消、恢复用例；业务规则需推导组合、幂等副作用或断言有效性不清时，读取 `references/scenarios.md` 的方法与正反例。run阶段允许补最少必要输入以写出有意义断言。
4. 选择能捕获目标错误、反馈快且不过度依赖实现细节的边界，验证稳定可观察契约，不一律推到最高层。需要语言/框架执行细节时读取 `references/language-testing.md`，沿用现有风格。避免只测mock；幂等/重试/副作用契约可验证关键调用次数。集成测试可使用隔离真实数据库，不混淆单元mock与集成依赖。
5. 执行记录命令、环境、退出码、关键输出；失败按下方分类后动作，不直接改实现。隔离flaky须记录原因和修复计划，不“重跑到绿”掩盖失败。
6. 报告规则覆盖、执行结果、修复摘要（如有）、缺口与相关完整日志位置。覆盖率不代表正确性；性能/安全测试参考 references/performance-security.md。

## 失败分类与修复回路
失败先分类，再决定动作：

| 类型 | 动作 |
|---|---|
| 环境/工具缺失 | 报告缺口，不改代码 |
| 用例缺陷（期望/断言错误、不稳定） | 修正用例并说明原因；不因当前实现如此就放宽期望 |
| 需求/口径不清 | 列未决并停下确认，不猜规则 |
| 实现缺陷 | 进入修复回路 |

修复回路（仅实现缺陷）：
1. 授权前提：本次任务已包含实施授权（用户要求修好、build 后按风险的验证、或明确“测出问题就修”）。只说跑测试/看测试时只报告并询问是否修。
2. 保留失败用例作为回归证据，交 `dv-build` 按其规则最小修复：复用台账、不顺手重构、不新增依赖、不放宽或跳过断言。
3. 需要改接口/契约、超4个文件或产品决策未定时停下要授权，不自行扩大范围。
4. 复测失败用例→同模块相关套件→lint/typecheck（按风险），记录命令与退出码。
5. 同一缺陷最多2轮修复；仍失败或根因不明交 `dv-debug`，附证据，不连续盲改。

## 自检
不安装新框架、不用生产数据或对生产压测；需要额外权限先确认。design文档和run测试代码权限明确，测试期望不能仅因为当前实现如此就定义为正确。修复只在授权与失败分类允许时进行，不跳过/削弱断言掩盖失败，不commit/push。
