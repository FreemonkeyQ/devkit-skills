# 审计

只报告，不改代码、不改测试、不装依赖。**结论必须有可复现的命令与数字。**

## 适用 / 不适用

适用：想知道测试能不能抓 bug；找高复杂度方法；全库健康体检；评估技术债。

不适用：要修 bug → `/dv-debug`；要改代码 → `/dv-build`；要审某个 diff → `/dv-review`。

## 三项检查

### 1. 测试有效性（突变测试）

1. 先确认项目已有突变工具（`pitest` / `mutmut` / `stryker` / `go-mutesting` 等）。**没有就明确报告「无可用工具」，不自行安装。**
2. 用项目既有配置跑一次，收集：突变体总数、杀死数、存活数、存活突变体清单（文件:行）。
3. 分析存活突变体：是测试没覆盖，还是断言太弱。
4. 边界：不修改代码或测试来「提升分数」。

### 2. 复杂度风险

1. 判断能否计算 CRAP（复杂度 × 未覆盖风险）。缺覆盖率数据就降级为纯圈复杂度 + 行数 + 参数个数。
2. 列出高风险方法：按分数排序，标出「难安全修改」的理由（分支多、依赖多、无测试）。
3. 边界：不因为复杂就建议拆——先问「有没有变更需求」。

### 3. 全库健康

- 依赖方向是否有环
- 重复实现（同一逻辑多处）
- 无测试覆盖的核心模块
- 明显的安全面（拼接 SQL、未校验输入、硬编码凭据）

## 产物

`docs/audits/<YYYY-MM-DD>-<slug>.md`：

```markdown
# <范围> 审计
## 结论（3 条以内）
## 证据
| 检查 | 命令 | 数字 |
## 风险清单（按严重度）
## 建议（给 /dv-build 或 /dv-plan 的具体动作）
## 未覆盖范围（明确写了没查什么）
```

## 自检

- [ ] 每个数字都有命令和输出
- [ ] 工具不存在时明确说明，没有假装跑过
- [ ] 建议是可执行的下一步，不是泛泛而谈
- [ ] 写清没查的部分
- [ ] 没有改动任何代码

## 反合理化

| 我本来想说 | 现实 |
|---|---|
| 「覆盖率 75%，还行」 | 覆盖率高不等于断言有效，突变测试才回答「能不能抓 bug」 |
| 「装个新工具跑跑看」 | 审计不改环境 |
| 「这个类太复杂了，建议拆」 | 复杂不等于需要拆，先看变更频率 |
| 「没跑工具，凭经验看」 | 没有数字的审计是意见 |
