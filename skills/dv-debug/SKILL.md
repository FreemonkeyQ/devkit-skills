# 基于证据调试

## 适用 / 不适用
具体报错、失败测试、性能回归、偶发异常；无症状全库检查用audit，审diff用review。只诊断请求不得自动修复。

## 流程
1. 明确症状、版本、环境、发生条件、近期变更。允许读代码、日志、配置与追踪来构造假设和复现；假设必须标记，不当作根因。
2. 尽量建立能捕获症状的反馈环：失败测试、API/CLI脚本、浏览器、请求重放、最小子系统、属性测试、差分或二分。按相关性选择，不机械试遍十种方式。根因未明、有竞争假设、偶发/并发或无法复现时，读取 `references/diagnosis.md`，用预测与实验更新假设。
3. 提升信号准确性、速度和稳定性；偶发问题记录复现率与试验条件，不能把“没再出现”证明为修复。
4. 一次验证一个假设，保留反证；定位后提出最小修复。用户明确要求修复时实施，重大新范围/生产埋点/远程写入另外确认。
5. 补回归或等价验证，修复前后证据可对照；无法复现时交付证据、仍存假设、下一步及验证限制，允许静态定位但不伪称已实证修复。
6. 按任务要求留调试记录，review改动后done汇报。不会自动提交推送。

## 自检
能区分事实/推断/验证缺口；不通过吞异常隐藏故障；日志与报告不泄露凭据。快速并非硬要求：复杂集成复现分钟级也可接受，只需说明成本。
