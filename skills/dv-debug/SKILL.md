# 调试

先有**一个能红的复现**，再谈原因。没有它，读代码猜原因属于违规。

## 适用 / 不适用

适用：具体报错；失败测试；性能回归；偶发失败；行为异常但有明确症状。

不适用：泛泛问「这段代码有什么问题」→ `/dv-review`；想评估架构 → `/dv-arch`；没有症状只想体检 → `/dv-audit`。

## 流程

### Phase 1 · 建反馈环（本技能的核心）

按顺序尝试，直到有一个**跑一次就红**的东西：

1. 在可达的最高接缝写失败测试
2. curl / HTTP 脚本打运行中的服务
3. CLI 调用 + 固定输入，diff 输出
4. 无头浏览器脚本（Playwright），断言 DOM / console / network
5. 重放抓到的请求 / 事件日志
6. 最小可运行子集（单服务 + mock 依赖）
7. 财产测试 / 模糊输入，1000 次找失败模式
8. 二分：在两个已知状态间自动化「起-查-停」，配合 `git bisect run`
9. 差分：同一输入跑新旧版本，比输出
10. 必须人点：用结构化脚本驱动人，输出仍回灌

### Phase 2 · 收紧

- 更快？缓存初始化、缩小测试范围
- 信号更准？断言**症状本身**，不是「没崩」
- 更确定？固定时间、随机种子、隔离文件系统、冻结网络

### Phase 3 · 定位与修复

二分 / 假设-验证 / 加临时埋点，消耗反馈环。找到原因后：

- 写**回归测试**（在 Phase 1 的环上）
- 做最小修复
- 环转绿

### Phase 4 · 收尾

把「复现命令 + 根因 + 修复 + 回归测试位置」写进 `docs/research/<date>-<slug>.md`（若根因涉及设计缺陷，建议 `/dv-arch shape`）。

## 完成判据

Phase 1 结束必须能贴出**一条已经跑过的命令 + 它的输出**，且满足：

- [ ] 能红：驱动真实代码路径，断言用户看到的症状
- [ ] 确定性：每次结论一致（偶发则已把复现率提到可调试）
- [ ] 快：秒级
- [ ] 可无人运行

任何一项不满足，**不许进入 Phase 3**。

## 做不到时的正确做法

明确说明做不到，列出已尝试的方法，向用户要：能复现的环境、抓到的产物（HAR / 日志 / core dump / 带时间戳的录屏）、或加临时生产埋点的许可。**不要在没有环的情况下开始猜。**

## 自检

- [ ] 贴出了 Phase 1 的命令与输出
- [ ] 回归测试在修复前是红的
- [ ] 修复后全量测试通过
- [ ] 记录了根因，不只是「改了什么」

## 反合理化

| 我本来想说 | 现实 |
|---|---|
| 「从代码看应该是这里」 | 没有红过的环，这只是猜测 |
| 「偶发问题不好复现，先改改看」 | 目标不是完美复现，是把复现率提到可调试 |
| 「加个 try/catch 先不报错」 | 掩盖症状会让下一层问题更贵 |
| 「修好了，测试也过了，不用写回归」 | 没有回归测试，同一个 bug 会回来 |
